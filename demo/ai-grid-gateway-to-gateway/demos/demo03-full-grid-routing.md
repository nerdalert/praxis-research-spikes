# Demo 3 — Full Grid: Clusters + Cloud + APIs

## Overview

One consumer gateway routes across all four backend kinds defined in the Grid
scoring model — local/self-hosted, remote/self-hosted, cloud-managed, and
API-provider — with the correct scoring order and gateway-level credential injection.

The overlay is generated by the Grid operator from four `InferenceProvider` resources
in a single `GridNetwork`.  The consumer gateway config is built by the xtask harness
from that overlay, and each model name is unique to exactly one backend class so routing
is structurally unambiguous.

## Topology

```
Consumer (kind-grid-consumer)
  ├─ model-east → gateway-site-east ──mTLS──► site-east provider gateway
  │                                              └─► mock-epp → mock-openai-provider
  ├─ model-west → gateway-site-west ──mTLS──► site-west provider gateway
  │                                              └─► mock-epp → mock-openai-provider
  ├─ model-cloud → gateway-op-e2e-fg-cloud ──HTTP──► mock-cloud-provider (in consumer cluster)
  └─ model-api → gateway-op-e2e-fg-api ──HTTP──► mock-api-provider (in consumer cluster)
                  ↑ Authorization: Bearer grid-api-fallback-secret (injected by gateway)
```

## Backend Kinds and Scoring

| Model | Backend Kind | Locality Score | Cluster Identity |
|---|---|---|---|
| `model-east` | `local` | 1.0 | `site-east` (via `routingClusterRef`) |
| `model-west` | `remote` | 0.5 | `site-west` (via `routingClusterRef`) |
| `model-cloud` | `cloud_managed` | 0.2 | `op-e2e-fg-cloud` (provider name) |
| `model-api` | `api_provider` | 0.1 | `op-e2e-fg-api` (provider name) |

Overlay candidates appear in this exact order (`local` first, `api_provider` last).

## What Each Model Proves

### `model-east` — Local/self-hosted path (site-east)

Proves the full provider gateway chain:

```
consumer → mTLS → praxis-provider (site-east) → ext_proc/mock-epp → endpoint_selector → mock-openai-provider
```

- `routingClusterRef = "site-east"` → overlay candidate `site = "site-east"`
- consumer load_balancer `gateway-site-east` → mTLS → site-east NodePort
- response `model` field echoes `"model-east"` — confirming the backend

### `model-west` — Remote/self-hosted path (site-west)

Same provider gateway chain, different cluster:

```
consumer → mTLS → praxis-provider (site-west) → ext_proc/mock-epp → endpoint_selector → mock-openai-provider
```

- `backendKind = "remote"`, `routingClusterRef = "site-west"`
- Scored lower than `model-east` (remote locality 0.5 vs local 1.0)
- response `model` field echoes `"model-west"`

### `model-cloud` — Cloud-managed path

Proves routing to a cloud-managed endpoint without the provider gateway mTLS chain:

```
consumer → plain HTTP → mock-cloud-provider (in consumer cluster)
```

- `backendKind = "cloud_managed"`, no `routingClusterRef` → candidate `site = "op-e2e-fg-cloud"`
- consumer load_balancer `gateway-op-e2e-fg-cloud` → in-cluster DNS, no TLS
- response `model` field echoes `"model-cloud"`

### `model-api` — API-provider path with credential injection

Proves gateway-level credential injection plus API-provider routing:

```
consumer → filter: headers / request_set (Authorization: Bearer grid-api-fallback-secret)
         → plain HTTP → mock-api-provider (in consumer cluster)
```

- `backendKind = "api_provider"`, `providerKind = "anthropic"`, no `routingClusterRef`
- consumer injects `Authorization: Bearer grid-api-fallback-secret` for all requests
- mock-api-provider validates Bearer token presence → accepts
- response `model` field echoes `"model-api"`

The credential injection mechanism uses Praxis's built-in `filter: headers` / `request_set`
filter, which is available in the `praxis-ai:llmd-ext-proc` build.

## Credential Injection Note (API Provider)

The consumer Praxis config includes:

```yaml
- filter: headers
  request_set:
    - name: "Authorization"
      value: "Bearer grid-api-fallback-secret"
```

This applies to all requests in the consumer filter chain.  Local and remote provider
gateways ignore the injected `Authorization` header (they authenticate via mTLS).  The
cloud-managed mock (openai mode) accepts any Bearer token.  The API-provider mock also
accepts any Bearer token, but its purpose in this demo is to prove the routing path.

In production, the injected token would be read from a Kubernetes Secret referenced by
`InferenceProvider.spec.auth.secret_ref`.

## Cloud-Managed Mock Limitation

The `mock-cloud-provider` is the same `grid-mock-providers --provider openai` binary used
for other mocks.  It represents a cloud-managed API endpoint in name only — it does not:

- Implement AWS SigV4, Google OAuth2, or Azure token exchange
- Enforce cloud-provider-specific rate limits or quotas
- Use the cloud-managed endpoint URL format (e.g., `api.bedrock.us-east-1.amazonaws.com`)

The `backendKind = "cloud_managed"` label in the `InferenceProvider` affects scoring
(locality score 0.2) and overlay candidate ordering, but has no effect on the actual
HTTP connection or authentication.

## What This Does Not Prove

| Capability | Status |
|---|---|
| Real Bedrock / Vertex / OpenAI endpoints | Not proven — uses local mocks |
| Real SigV4 / OAuth2 credential generation | Not proven — uses static Bearer token |
| Production Kubernetes Secret projection | Not proven — token is static in consumer config |
| Per-request dynamic scoring | Not proven — all providers have static scores |
| Budget enforcement | Not proven — no cost or rate-limit policy |
| Provider gateway unavailable → cloud fallback | Not proven — separate Demo 9 scope |
| SWIM/CRDT-discovered remote providers | Not proven — all four use static operator fixtures |
